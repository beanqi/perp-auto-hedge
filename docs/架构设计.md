# 架构设计

## 1. 设计原则

本设计只覆盖当前业务需要的三件事：

1. 模块划分；
2. 数据流转；
3. 状态机维护。

设计原则：

```text
Simple > Clever
Concrete > Abstract
Explicit > Magical
Current Requirement > Future Flexibility
Small Diff > Architecture Rewrite
```

整体采用：

```text
单进程
+ 事件驱动
+ Pair 为核心运行单元
+ Engine 单点维护状态
```

当前阶段不引入微服务、Actor Framework、内部消息总线、复杂 DDD 分层或通用工作流框架。

# 2. 模块划分

建议目录：

```text
src/
├── main.rs
├── config.rs
├── exchange/
│   ├── mod.rs
│   ├── binance/
│   │   ├── mod.rs
│   │   ├── spot.rs
│   │   └── perp.rs
│   ├── okx/
│   │   ├── mod.rs
│   │   ├── spot.rs
│   │   └── perp.rs
│   └── ...
├── market.rs
├── pair.rs
├── strategy.rs
├── risk.rs
├── execution.rs
├── state.rs
├── storage.rs
└── engine.rs
```

核心边界：

```text
Exchange 只处理交易所协议与事实，不做业务决策
Strategy 只计算交易价值
Risk 只判断是否允许承担风险
Execution 只负责把确定的计划执行出去
Engine 是状态的唯一修改者
```

## 2.1 main.rs

只负责启动：

```text
读取配置
→ 初始化 Storage
→ 初始化 Exchange
→ 初始化 Engine
→ Engine.run()
```

不要在 `main.rs` 中放策略、订单或状态机逻辑。

## 2.2 config.rs

只保存全局配置，对应业务设计中的机会参数、成交参数、风控参数和模型参数。

不为单独 Pair 设置策略参数，除非属于交易所本身的 instrument metadata。

## 2.3 exchange/

负责与交易所通信，并把不同交易所、不同市场类型的数据转换成统一结构。

### 现货与合约必须分开

同一个交易所下，Spot 和 Perp 使用独立 adapter：

```text
exchange/binance/spot.rs
exchange/binance/perp.rs

exchange/okx/spot.rs
exchange/okx/perp.rs
```

原因很直接：

```text
Spot API != Perp API
Spot WebSocket != Perp WebSocket
Spot Instrument != Perp Instrument
Spot Account / Borrow != Perp Position / Margin
```

即使某个交易所当前两套 API 很相似，也不要把具体 endpoint、请求参数和消息格式强行做成一套实现。

`exchange/mod.rs` 只负责统一系统内部使用的数据结构和调用语义，不隐藏 Spot / Perp 的真实差异。

市场必须显式包含类型：

```text
MarketId {
    exchange,
    market_type: Spot | Perp,
    symbol,
}
```

Pair 的每条 Leg 都引用完整 `MarketId`，不能只用 `exchange + symbol` 推断市场类型。

### 通信方式

Exchange adapter 的通信分为三类：

```text
REST / Request API
    → Instrument Catalog
    → 启动时 Balance / Position / OpenOrder 查询
    → Reconcile / 异常恢复时主动查询

Market WebSocket
    → OrderBook
    → Funding
    → Account / Position / Order Update
    → Fill

Trading WebSocket
    → Place Order
    → Cancel Order
```

下单统一使用 Trading WebSocket，不通过 REST 发送订单。

撤单也优先走同一 Trading WebSocket，保证交易指令走一条明确路径。

REST 主要用于启动、对账和恢复，不进入正常下单主链路。

Spot 和 Perp 可以各自维护独立的 Market WebSocket / Trading WebSocket 连接，因为它们的 endpoint、认证方式、channel 和消息格式可能完全不同。

### 统一输出

Exchange adapter 对系统内部统一输出：

```text
Instrument
OrderBook
Position
Balance
Order
Fill
Funding
BorrowInfo
```

其中 Spot adapter 负责 Spot Instrument、Spot Order、Balance、Borrow 等现货事实；Perp adapter 负责 Contract Instrument、Position、Margin、Funding 等合约事实。

不要求两个 adapter 支持完全相同的交易所原生能力，只要求转换成系统当前需要的统一事实。

### OrderBook 统一使用多档结构

系统内部的 OrderBook 从一开始就使用多档结构：

```text
PriceLevel {
    price,
    quantity,
}

OrderBook {
    market_id,
    bids: Vec<PriceLevel>,
    asks: Vec<PriceLevel>,
    timestamp,
    sequence: Option<u64>,
}
```

约定：

```text
bids: price 从高到低
asks: price 从低到高
```

当前阶段只接交易所的一档实时深度，因此实际收到的数据通常是：

```text
bids = [best_bid]
asks = [best_ask]
```

但 Strategy、Risk、VWAP 和本地盘口撮合都不能假设只有一档。

后续切换 L2 增量深度时，只修改 Exchange adapter：

```text
L2 Snapshot
+ Incremental Update
→ Exchange adapter 维护本地 OrderBook
→ 输出相同的 OrderBook 多档结构
```

下游 `MarketStore / Strategy / Risk / Execution` 不因为 L1 切换 L2 而修改数据模型。

Exchange 不知道 Residual、Z、Half-life、EV，也不决定是否开平仓。

## 2.4 market.rs

维护最新市场快照：

```text
MarketId
  → Latest OrderBook
  → Latest Funding
  → Market Status
  → Latest Timestamp
```

`MarketStore` 中的 `OrderBook` 始终是统一多档结构。当前 L1 接入只是每侧最多一档，不改变结构。

本地 VWAP / 盘口撮合统一按照多档逐档消耗：

```text
目标数量 Q
→ 从最优价开始
→ 逐档 consume quantity
→ 累计 filled quantity / notional
→ 计算 VWAP / worst price
```

例如买入时：

```text
asks[0]
→ asks[1]
→ asks[2]
→ ...
```

卖出时：

```text
bids[0]
→ bids[1]
→ bids[2]
→ ...
```

如果当前可见深度无法覆盖目标数量：

```text
available_quantity < target_quantity
→ DepthInsufficient
```

不能把最后一档价格外推到剩余数量，也不能假设剩余数量可以按同一价格成交。

因此当前只接一档深度时，目标数量大于一档可成交数量的 Candidate 应被流动性检查阻止；未来切换 L2 后，同一套多档撮合逻辑会自然使用更多档位。

`MarketStore` 只保存当前事实，不负责长期统计历史。

## 2.5 pair.rs

系统围绕 Pair 运行，而不是围绕 Exchange 运行。

```text
Pair {
    base_asset,
    leg_a,
    leg_b,
}
```

其中 `leg_a / leg_b` 必须包含完整 `MarketId`，显式区分 Spot / Perp。

同一个 Pair 同时可以评估：

```text
A Short / B Long
A Long  / B Short
```

不为两个方向创建两个重复 Pair。

### PairBuilder

负责：

```text
Instrument Catalog
→ 按 Base Asset 分类
→ 两两组合
→ 校验经济含义 / Quote / Contract Multiplier
→ 生成 Pair
```

动态的流动性、Regime、借币、P(revert) 等条件不用于频繁创建或删除 Pair，只决定当前是否允许交易。

### PairRuntime

每个 Pair 对应一个运行时对象：

```text
PairRuntime
├── Pair
├── PairState
├── PairHistory
├── PairMetrics
├── LatestEvaluation
└── ActiveTrade
```

这是一个 Pair 所有运行状态的聚合点。

## 2.6 strategy.rs

Strategy 直接实现业务计算，不继续拆成大量 Service。

计算链路：

```text
Multi-level VWAP
→ Entry / Close Spread
→ Normal Spread μ
→ Residual
→ MAD / σ
→ Z / Percentile
→ Half-life
→ Velocity
→ P(revert)
→ Regime
→ Expected Convergence
→ Fee / Slippage / Funding / Borrow / Carry
→ Adjusted EV
→ Pair Score
```

VWAP 必须基于 `OrderBook.bids / asks` 逐档撮合，不直接读取单个 `best_bid / best_ask` 作为最终成交价格。

当前只有 L1 时，多档算法仍然运行，只是输入每侧只有一档。

### WATCHING 时

返回 `PairEvaluation`：

```text
metrics
entry_candidate
score
blocked_reason
```

`entry_candidate` 至少包含：

```text
direction
quantity
entry_vwap_a / entry_vwap_b
residual / z / percentile
half_life / p_revert
expected_holding_time
expected_net_pnl
expected_mae
score
```

如果任意一条腿的可见 OrderBook 无法覆盖目标数量，返回 `DepthInsufficient` / `liquidity_ok = false`，不生成可执行 Candidate。

Strategy 只回答：

> 从策略角度，这笔交易值不值得做。

### HOLDING 时

直接使用实际持仓数量重新计算：

```text
Current Close Spread
Remaining Convergence
Remaining Carry
Close Cost
Current P(revert)
Current Half-life
Current MAE Risk
Remaining EV
Regime
```

Close VWAP 同样按照当前多档 OrderBook 逐档计算。

返回是否应该退出以及退出原因。

## 2.7 risk.rs

Strategy 回答“想不想交易”，Risk 回答“允不允许交易”。

维护：

```text
Pair Position
Asset Position
Exchange Exposure
Total Exposure
Balance / Margin
Borrow Availability
Opening Reservation
```

开仓前通过 `check_open()` 检查：

```text
Min / Max Order Notional
Max Pair Position
Max Asset Position
Max Exchange Exposure
Max Total Exposure
Max Orderbook Participation
Visible Depth >= Target Quantity
Borrow / Margin Availability
```

通过后先 `reserve()`，防止多个 Pair 同时重复占用同一风险预算。

持仓期间通过 `check_position()` 检查账户、保证金、交易所和全局风险异常。

## 2.8 execution.rs

Execution 只执行已经确定的交易计划。

例如：

```text
OpenPlan {
    trade_id,
    leg_a: SELL 0.1 BTC,
    leg_b: BUY  0.1 BTC,
}
```

Execution 不重新判断 Z、Percentile、EV 或 Pair Score。

它只处理：

```text
通过 Trading WebSocket 下单
通过 Trading WebSocket 撤单
订单 Ack / Rejected
订单状态
成交数量
超时
部分成交
两腿数量差异
```

正常执行链路：

```text
Execution
→ 根据 leg.market_id 找到 Spot / Perp adapter
→ Trading WebSocket PlaceOrder
→ Order Ack / Order Update / Fill
→ Execution 聚合两腿结果
→ ExecutionEvent
```

Execution 不直接拼交易所原生 WebSocket 消息；具体协议由对应 Exchange adapter 处理。

如果 Trading WebSocket 断开或未 Ready：

```text
禁止发送新的 Open Order
```

需要降低风险时，优先恢复 Trading WebSocket；如果无法确认订单是否成功发送或交易所状态不明确，则进入 Reconcile / RECOVERING，而不是盲目重发。

最终产生 `ExecutionEvent`：

```text
OpenCompleted
OpenFailedNoFill
ExecutionImbalance
CloseCompleted
CloseFailed
```

### 双腿执行异常

如果：

```text
A 成交 0.1 BTC
B 成交 0.03 BTC
```

这不是普通失败，而是 0.07 BTC 的裸露风险。

必须显式返回：

```text
ExecutionImbalance
```

随后 Pair 进入 `RECOVERING`。

Recovery 只做一件事：恢复 Delta Neutral / Flat，不再重新判断这笔交易的 EV。

## 2.9 state.rs

保存：

```text
SystemState
PairState
ActiveTrade
ExecutionContext
```

最重要的规则：

> PairState 只能由 Engine 修改。

Strategy、Risk、Exchange、Execution 都不能直接改变 PairState。

## 2.10 storage.rs

只持久化无法安全丢失的数据：

```text
Pair 历史统计输入
Active Trade
Completed Trade
```

Pair 历史不保存完整 OrderBook，只保存策略恢复所需的衍生 observation，例如：

```text
timestamp
pair_id
spread
residual
相关统计输入
```

关键状态转换必须持久化：

```text
WATCHING -> OPENING
OPENING  -> HOLDING
HOLDING  -> CLOSING
CLOSING  -> WATCHING
任意执行状态 -> RECOVERING
```

## 2.11 engine.rs

Engine 是 orchestrator，不包含复杂策略公式。

主流程：

```text
收到事件
→ 更新数据
→ 找到受影响 Pair
→ 调用 Strategy
→ 调用 Risk
→ 根据 PairState 决定动作
→ 必要时调用 Execution
→ 更新 State
→ Storage 持久化
```

系统的所有状态变化统一经过 Engine。

# 3. 数据流

系统主要处理四类输入：

```text
MarketEvent
AccountEvent
ExecutionEvent
TimerEvent
```

统一进入 Engine：

```text
Spot / Perp Market WebSocket ── MarketEvent ──┐
Spot / Perp Private WebSocket ─ AccountEvent ─┤
Execution ────────────────────────────────────> Engine
Timer ────────────────────────────────────────┘
```

交易指令单独走：

```text
Engine
→ Execution
→ Spot / Perp Trading WebSocket
→ Exchange
```

## 3.1 启动流程

```text
加载 Config
→ 加载 Storage
→ 初始化各 Exchange 的 Spot / Perp adapter
→ 获取 Instrument Catalog
→ 统一 Instrument 规格
→ PairBuilder.build()
→ 创建 PairRuntime
→ 读取 ActiveTrade
→ 查询 Exchange Position / OpenOrder
→ Reconcile
→ 启动 Market WebSocket
→ 启动 Private / Trading WebSocket
→ 等待 Trading WebSocket Ready
→ 恢复 Pair History
→ RUNNING
```

本地状态不是仓位最终真相，交易所真实 Position 才是。

Trading WebSocket 未 Ready 时不能进入允许新开仓的正常执行状态。

## 3.2 行情流

当前阶段：

```text
Exchange L1 / BBO WebSocket
→ Spot / Perp adapter
→ 转换成统一 OrderBook
   bids = [best_bid]
   asks = [best_ask]
→ MarketEvent
→ Engine
→ MarketStore.update()
→ 找到引用该 Market 的 Pair
→ Evaluate Pair
```

后续 L2：

```text
Exchange L2 Snapshot + Incremental Update
→ Spot / Perp adapter 维护本地多档 OrderBook
→ 输出相同 OrderBook
→ MarketEvent
→ 后续链路完全不变
```

某个市场变化时只重算受影响的 Pair，不全量扫描所有 Pair。

## 3.3 WATCHING 数据流

```text
MarketStore
→ 获取 A / B OrderBook
→ 按目标数量逐档撮合
→ 得到 A / B VWAP
→ Strategy.evaluate()
→ Spread
→ 更新 PairHistory
→ μ / Residual / Z / Percentile
→ Half-life / Velocity / P(revert)
→ Regime
→ Cost / Carry
→ Expected Net PnL
→ Pair Score
→ OpenCandidate
```

如果 A 或 B 任意一腿的可见深度不足：

```text
DepthInsufficient
→ liquidity_ok = false
→ 不生成可执行 OpenCandidate
```

此时只产生候选机会，不直接下单。

## 3.4 Opportunity 排名

Engine 维护最新 Candidate Set：

```text
所有 OpenCandidate
→ 删除过期 Candidate
→ 按 Pair Score 排序
→ 从高到低 Risk.check_open()
→ 直到风险预算耗尽
```

当前阶段不额外引入 Scheduler、Allocator 或 PortfolioOptimizer。

## 3.5 开仓流

```text
OpenCandidate
→ Risk.check_open()
→ Risk.reserve()
→ 生成 TradeId
→ WATCHING -> OPENING
→ Storage 保存 OPENING
→ Execution.open(OpenPlan)
→ Spot / Perp Trading WebSocket PlaceOrder
```

顺序必须是“先保存 OPENING，再通过 WebSocket 发送订单”。

每条 Leg 根据自己的 `MarketId.market_type` 路由到对应 Spot / Perp adapter，不能由 symbol 自动推断。

## 3.6 开仓成功

```text
Trading WebSocket Ack
+ Private WebSocket Order Update / Fill
→ Exchange adapter 统一事件
→ Execution
→ 两腿成交且数量匹配
→ OpenCompleted
→ Engine 验证 trade_id / execution_id
→ OPENING -> HOLDING
→ Reservation 转为实际 Exposure
→ Storage 保存 ActiveTrade
```

WebSocket Ack 只代表交易所接受请求，不代表已成交；状态转换以真实 Order Update / Fill 为准。

## 3.7 开仓失败

两边都没有成交：

```text
OPENING
→ 通过 Trading WebSocket 取消剩余订单
→ OpenFailedNoFill
→ 释放 Reservation
→ WATCHING
```

出现单腿或数量不匹配：

```text
OPENING
→ ExecutionImbalance
→ RECOVERING
```

如果 WebSocket 断线导致无法确认订单最终状态：

```text
不要直接重发
→ 主动查询 OpenOrder / Position
→ Reconcile
→ 根据真实状态继续 OPENING / HOLDING / RECOVERING
```

## 3.8 HOLDING 数据流

```text
MarketEvent
→ MarketStore
→ PairRuntime
→ 按实际持仓数量逐档计算 Close VWAP
→ Strategy.evaluate_holding()
```

基于实际持仓 Q 计算：

```text
Close VWAP
Remaining Convergence
Remaining Carry
Close Cost
P(revert)
Half-life
MAE Risk
Remaining EV
Regime
```

同时执行：

```text
Risk.check_position()
```

如果 Strategy Exit 或 Risk Exit 成立则进入 CLOSING，否则继续 HOLDING。

## 3.9 正常 / 风险平仓

正常条件：

```text
RemainingEV <= ExitEV
```

风险条件：

```text
Regime Break
Time Stop
Residual Stop
Reversion Failure
Liquidity Collapse
Exchange Risk
Account Risk
Execution Risk
```

统一走：

```text
HOLDING
→ CLOSING(reason)
→ Storage
→ Execution.close()
→ Trading WebSocket PlaceOrder
```

不要为不同退出原因创建多个 Closing 状态，只记录 `CloseReason`。

## 3.10 Recovery 数据流

```text
ExecutionImbalance
→ Engine
→ PairState = RECOVERING
→ 停止 Strategy Entry
→ 通过 Trading WebSocket 取消该 Trade 的未完成订单
→ 查询真实 Position
→ 计算裸露数量
→ Execution.flatten()
→ Trading WebSocket PlaceOrder
→ 再次确认 Position
```

恢复成功：

```text
RECOVERING -> WATCHING
```

无法安全恢复：

```text
RECOVERING -> HALTED
SystemState = HALTED
```

# 4. 状态机

状态机只分两层：

```text
SystemState
PairState
```

不要继续增加更多独立状态机。

## 4.1 SystemState

只保留：

```text
STARTING
RUNNING
HALTED
```

```text
STARTING ──初始化 / Reconcile 成功──> RUNNING
                                      │
                                      │ 严重系统风险
                                      ▼
                                    HALTED
                                      │
                                      │ 人工处理 + Reconcile
                                      ▼
                                   STARTING
```

### STARTING

用于连接交易所、加载数据、查询真实仓位、构建 Pair、恢复历史、执行 Reconcile，并确认 Market / Private / Trading WebSocket 已进入可用状态。

禁止新开仓。

### RUNNING

正常执行行情计算、机会发现、开仓、持仓和平仓。

如果 Trading WebSocket 不可用，禁止新的 Open；是否进入 HALTED 取决于当前是否存在无法安全降低的风险仓位。

### HALTED

用于无法自动确认安全状态的严重异常，例如：

```text
裸露仓位无法恢复
交易所仓位与本地状态严重不一致
关键账户状态异常
Trading WebSocket 不可用且无法安全降低风险
Storage 无法可靠记录关键状态
```

HALTED 禁止新开仓，但允许查询、撤单和降低风险。

HALTED 不自动恢复，必须重新执行 Reconcile。

## 4.2 PairState

每个 Pair 只维护：

```text
WARMING_UP
WATCHING
OPENING
HOLDING
CLOSING
RECOVERING
HALTED
```

主路径：

```text
WARMING_UP
    ↓
WATCHING
    ↓
OPENING
    ↓
HOLDING
    ↓
CLOSING
    ↓
WATCHING
```

异常路径：

```text
OPENING / CLOSING
       ↓
  RECOVERING
       ↓
WATCHING / HALTED
```

### WARMING_UP

历史窗口不足时使用。

允许接收行情和更新统计，禁止开仓。

### WATCHING

当前没有仓位和执行中的订单，允许寻找机会。

`WATCHING` 不等于一定允许开仓。

使用显式 Entry Gate：

```text
data_fresh
pair_quality_ok
liquidity_ok
regime_ok
account_ok
borrow_ok
risk_ok
trading_ws_ready
```

Gate 失败只记录 `blocked_reason`，不要增加 `REGIME_BLOCKED`、`LIQUIDITY_BLOCKED` 等状态。

### OPENING

进入时必须已经存在：

```text
trade_id
direction
target_quantity
open_plan
entry_metrics
created_at
Risk Reservation
```

禁止再次生成 OpenCandidate 或重复发送 OpenPlan。

转换：

```text
两腿完成且数量匹配 -> HOLDING
零成交失败           -> WATCHING
单腿 / 数量不匹配    -> RECOVERING
订单状态无法确认      -> Reconcile 后决定
```

### HOLDING

维护完整 `ActiveTrade`，至少包括：

```text
trade_id
pair_id
direction
leg_a_quantity / leg_b_quantity
entry_price_a / entry_price_b
opened_at
entry_residual / z / percentile
entry_half_life / p_revert
expected_holding_time
expected_mae
```

持仓期间禁止再次开仓。

### CLOSING

维护：

```text
trade_id
close_reason
target_close_quantity
started_at
```

`CloseReason` 可以是：

```text
RemainingEV
RegimeBreak
TimeStop
ResidualStop
ReversionFailure
LiquidityCollapse
AccountRisk
ExchangeRisk
Manual
```

两边全部归零：

```text
CLOSING -> WATCHING
```

没有任何成交且原仓位仍完整对冲：

```text
CLOSING -> HOLDING
```

出现单腿风险：

```text
CLOSING -> RECOVERING
```

### RECOVERING

这是 Pair 优先级最高的状态。

只执行：

```text
取消剩余订单
→ 查询真实 Position
→ 计算 Net Exposure
→ 降低 / 消除裸露 Exposure
→ 再次确认 Position
```

不再计算新的 Entry，也不参与 Pair Ranking。

### HALTED

表示自动逻辑无法确认 Pair 的安全状态。

禁止 Strategy Entry 和 Open，只允许查询、撤单、Recovery 和人工处理。

恢复前必须重新 Reconcile。

# 5. 状态维护规则

## 5.1 Engine 是唯一 State Writer

错误方式：

```text
Strategy 修改 OPENING
Execution 修改 HOLDING
Risk 修改 CLOSING
```

正确方式：

```text
Strategy  -> Decision
Risk      -> Permission / RiskEvent
Execution -> ExecutionEvent
               ↓
             Engine
               ↓
            PairState
```

即：

```text
Strategy 提建议
Risk 给许可
Execution 给事实
Engine 改状态
```

## 5.2 使用显式 match

当前状态很少，直接使用 Rust `match`，不引入 StateMachineFramework、TransitionRegistry 或 RuleEngine。

```rust
match pair.state {
    PairState::Watching => {
        // Entry
    }
    PairState::Opening(_) => {
        // Opening ExecutionEvent
    }
    PairState::Holding(_) => {
        // Holding evaluation
    }
    PairState::Closing(_) => {
        // Closing ExecutionEvent
    }
    PairState::Recovering(_) => {
        // Recovery
    }
    _ => {}
}
```

## 5.3 TradeId / ExecutionId

每笔交易生成唯一 `trade_id`，每次执行动作生成唯一 `execution_id`。

所有 `ExecutionEvent` 必须携带：

```text
pair_id
trade_id
execution_id
```

Engine 只有在当前 Pair、State、trade_id、execution_id 全部匹配时才处理事件。

这样可以避免延迟 Fill 或旧订单事件修改已经进入下一阶段的 Trade。

## 5.4 持久化顺序

涉及真实资金的状态变化：

```text
更新内存 State
→ 持久化 State
→ 发送 Execution Command
```

例如：

```text
WATCHING
→ 生成 trade_id
→ OPENING
→ Storage.save()
→ Execution.open()
→ Trading WebSocket PlaceOrder
```

以及：

```text
HOLDING
→ CLOSING
→ Storage.save()
→ Execution.close()
→ Trading WebSocket PlaceOrder
```

Trading WebSocket 请求必须携带可关联到 `execution_id` 的 client order id / request id，确保 Ack、Order Update 和 Fill 能关联回当前执行上下文。

## 5.5 Restart / Reconcile

程序重启不能只读取本地 PairState 后继续执行。

必须使用：

```text
Storage ActiveTrade
+
Exchange OpenOrder
+
Exchange Position
↓
Reconcile
```

典型规则：

```text
Local OPENING + Exchange Flat
    -> WATCHING

Local OPENING + 完整双边仓位
    -> HOLDING

Local HOLDING + 完整双边仓位
    -> HOLDING

Local HOLDING + Exchange Flat
    -> 记录外部平仓异常 -> WATCHING

任意 Local State + 单腿 / 数量不匹配
    -> RECOVERING

无法判断
    -> HALTED
```

WebSocket 断线重连后同样执行一次轻量 Reconcile，不能假设断线期间没有订单状态变化。

# 6. 最终主链路

整个系统最终保持一条明确链路：

```text
Spot / Perp Exchange Adapter
   ↓ Market WebSocket
OrderBook（统一多档结构；当前每侧一档）
   ↓
MarketStore
   ↓
PairRuntime
   ↓
Strategy（按多档撮合计算 VWAP）
   ↓
Engine
   ↓
Risk
   ↓
PairState
   ↓
Execution
   ↓
Spot / Perp Trading WebSocket
   ↓
Exchange
   ↓ Order Update / Fill
ExecutionEvent
   ↓
Engine
   ↓
PairState
```

始终保持四个边界：

```text
Exchange 只处理交易所协议与事实，不做业务决策
Strategy 只计算交易价值
Risk 只判断是否允许承担风险
Engine 是 PairState 唯一修改者
```

行情层保持一个重要约束：

```text
内部永远使用多档 OrderBook
当前数据源 = L1 实时深度
未来数据源 = L2 Snapshot + Incremental Update
下游接口不变
```

本地盘口撮合也始终使用同一套多档逻辑：

```text
从最优价逐档消耗数量
→ 计算真实可见深度下的 VWAP
→ 深度不足则显式失败
```

Pair 正常生命周期：

```text
WARMING_UP
→ WATCHING
→ OPENING
→ HOLDING
→ CLOSING
→ WATCHING
```

双腿执行异常统一进入：

```text
OPENING / CLOSING
→ RECOVERING
→ WATCHING 或 HALTED
```

这就是当前业务需求需要的全部核心架构。
